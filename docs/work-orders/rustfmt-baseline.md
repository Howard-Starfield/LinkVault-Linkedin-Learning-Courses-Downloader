# Work order: establish a deterministic Rust formatting baseline

**Status:** Draft work order

**Owner:** LinkVault engineering

**Blocks:** Newspaper Clippings Phase 1 exit gate

**Related pull request:** Phase 1 clipping persistence and managed assets

## Problem

The Newspaper Clippings Phase 1 implementation passes its functional, migration,
persistence, clippy, Rust test, frontend build, and release checks, but the
repository-wide command below is not green:

```powershell
cargo fmt --manifest-path apps\desktop\src-tauri\Cargo.toml --check
```

The reported diff spans both Phase 1 files and pre-existing Rust files. The
clipping specification explicitly requires a green formatting gate and also
prohibits hiding unrelated formatting churn inside a feature PR. This work
order creates the separate prerequisite boundary required by
`AGENT-PHASE-002`.

## Goal

Make Rust formatting deterministic for a clean checkout of the default branch
without changing runtime behavior, schemas, IPC contracts, product copy,
dependencies, or release versions.

After this PR merges, the Phase 1 branch must rebase onto the result, format its
own touched Rust files under the same baseline, and rerun the Phase 1 exit gate.

## Mandatory investigation

Before editing, record:

```text
rustc --version --verbose
cargo --version
rustfmt --version
rustup show active-toolchain
```

Inspect:

- `apps/desktop/src-tauri/Cargo.toml`, including `rust-version = "1.77.2"`.
- Whether a `rust-toolchain.toml`, `rust-toolchain`, or `rustfmt.toml` already
  exists after rebasing.
- The complete `cargo fmt --check` file list on an otherwise clean `main`.
- Whether the mismatch changes when using the minimum supported Rust toolchain.
- Whether any formatter output changes macros, generated content, or files that
  should be excluded rather than formatted.

Do not assume that pinning `1.77.2` is correct merely because it is the minimum
compiler version. Prove the chosen baseline with a clean checkout and the full
verification commands.

## Acceptable implementation paths

Choose one evidence-backed path:

### Option A: pin a deterministic toolchain

Use this only when a specific stable toolchain makes the existing source tree
format-clean without a repository-wide rewrite and remains compatible with all
build/test requirements.

A toolchain pin must:

- Be explicit in a root `rust-toolchain.toml`.
- Include the `rustfmt` component.
- Be documented in developer/build instructions when needed.
- Work in Windows PowerShell and CI-style clean checkouts.
- Preserve the declared minimum/actual compiler policy honestly.

### Option B: one dedicated repository-wide formatting commit

Use this when the current supported formatter is authoritative and the source
baseline is simply stale.

The formatting commit must:

- Contain formatting-only Rust changes.
- Avoid TypeScript, CSS, Markdown reflow, dependency, schema, and behavior
  changes.
- Be mechanically generated by `cargo fmt`.
- Be easy to review separately from feature work.
- Be followed by a second commit only when tooling/documentation changes are
  genuinely required.

### Forbidden shortcuts

Do not:

- Remove `cargo fmt --check` from any specification or release gate.
- Replace it with a touched-files-only check.
- Add broad `#[rustfmt::skip]` annotations.
- Introduce behavior refactors while formatting.
- Format the Phase 1 feature branch inside this prerequisite PR.
- Change release versions or publish artifacts.
- Claim success from a dirty working tree.

Record exact versions, commands, exit codes, elapsed times, and any warnings.

## PR completion evidence

The final PR body must include:

- Root cause of the formatting mismatch.
- Chosen option and rejected alternative.
- Exact Rust/rustfmt versions.
- Full changed-file count.
- Confirmation that the diff is behavior-neutral.
- Verification table.
- Instructions for rebasing and reformatting the Phase 1 branch.
- Rollback procedure.
